> 이 문서를 그대로 Claude Code에 붙여 넣어 사용하세요. 상단부터 순서대로 지시입니다.

## 0. 너의 역할과 이번 작업의 범위

너는 KS-INFO "미니뱅크 마이그레이션 데모"의 **ASIS(레거시) 백엔드**를 구축한다.
스택은 **GnuCOBOL + 임베디드 SQL(EXEC SQL, GixSQL 프리컴파일) + Oracle**, 프론트 연결은 **CGI**다.
프론트엔드(JavaScript)는 **이미 완성되어 있고 무변경으로 재사용**한다. 따라서 **API 계약(엔드포인트 경로·메서드·요청/응답 JSON 형태·필드명)의 원천은 기존 프론트엔드 코드**다. 네가 임의로 만들지 말고 프론트에서 추출해 맞춘다.

TOBE(Java/Spring/PostgreSQL)와 現新비교 툴은 이번 작업 대상이 **아니다**. 다만 ASIS는 뒤에 現新비교 툴이 먹을 수 있는 **규격 맞는 입출력(EBCDIC 고정길이 파일 + DB 상태)**을 정확히 만들어야 한다.

**구현 대상**
- 온라인 5종 (CGI 프로그램): 残高照会 / 入金 / 出金(残高不足 체크) / 振込(원자적) / 取引明細照会
- 야간배치(日次バッチ): 当日取引 SORT → 계좌별 반영(control break) → 利息·手数料 계산 → 잔액 확정 → 更新後口座マスタ + 明細レポート(고정길이) 출력
- Oracle DDL + 카피북(copybook) + init/시드 데이터 적재 스크립트
- 빌드 파이프라인(gixpp → cobc) + Docker(compose 서비스 `asis-backend`, `oracle`) + nginx CGI 라우팅

### 0.1 확정된 설계 결정 (이 값들은 임의 변경 금지)
- **온라인 CGI 응답 인코딩 = UTF-8.** 브라우저(프론트)로 나가는 응답은 UTF-8. (DB 내부 저장·배치 출력은 아래처럼 EBCDIC 유지)
- **明細レポート 레코드 길이 = 58 byte로 통일.** T 레코드(실내용 29byte)는 뒤에 공백 29byte 패딩하여 58byte로 맞춘다.
- **利息는 普通預金(種別=1)에만 적용. 当座預金(種別=2)은 무이자(利息=0).**

## 2. 하드 제약 (절대 위반 금지)

- 컴파일러 **GnuCOBOL**. DB 접속은 **EXEC SQL + GixSQL 프리컴파일**. **Pro\*COBOL 사용 금지**.
- Oracle. 일본어 텍스트 컬럼(名義·摘要)은 **RAW**에 **EBCDIC(CP930) 바이트 원본** 저장. 디코딩 뷰 없음(원본 그대로).
- 金額은 COBOL **COMP-3** ↔ Oracle **NUMBER**.
- 프론트↔COBOL 연결은 **CGI**(고전 메인프레임 웹 패턴).
- 인코딩 CP930(SBCS 카나 + DBCS IBM 한자 cp300). **SO/SI(0x0E/0x0F)를 실제 바이트로 충실히 모델링.**
- **인코딩 경계 규칙(중요):**
  - DB 저장·조회, 배치 입력/출력(`MEISAI.RPT`) = **EBCDIC(CP930) 원본 유지**. Oracle↔COBOL은 RAW 무변환 통과.
  - 온라인 CGI가 브라우저로 내보내는 응답만 **UTF-8로 변환**. 변환 경로: `CP930 RAW → (팀 인코더) CP932 → UTF-8`.
- 고정길이 레코드의 **오프셋·바이트 길이·COMP-3 바이트 수를 설계서와 1바이트도 어긋나지 않게** 지킨다. (COMP-3 byte = floor(자릿수/2)+1)
- **이행 결정타 4개를 반드시 재현·보존**한다:
  1. 利息 端数処理 = **切り捨て**(1엔 미만 버림)
  2. SORT 정렬 순서 = **名義カナ 기준**(EBCDIC 순서로 노출)
  3. 漢字 고정길이 자름 = X(20) 안에서 SO/SI 포함 20바이트 경계 자름
  4. COMP-3(부호 니블·최대값·음수 포함)
- GixSQL 세부:
  - `gixpp` 호출 시 카피북 경로 `-I <경로>`, 확장자 `-ext ".,*.cpy,*.CPY"`로 COPY 전개
  - SQLCA는 `<gix설치>/share/gixsql/copy`를 COPY 경로에 추가
  - GixSQL은 Oracle 드라이버 지원 버전(1.0.18+, 가급적 1.0.20대) 사용
  - asis-backend 컨테이너에 Oracle Instant Client + charset(NLS_LANG) 명시 (RAW 무변환 통과와 직결)

## 3. 데이터 모델 / DDL / 카피북

상세설계 §3 그대로. 아래 표의 타입·길이를 정확히 반영해 **Oracle DDL**과 **COBOL 카피북**을 만든다.

### 3.1 口座 마스터 — `KOUZA`
| 물리명 | COBOL | Oracle | 비고 |
|---|---|---|---|
| KOUZA_NO | PIC 9(10) | NUMBER(10) | PK, 대역 체계 |
| MEIGI_KANJI | PIC X(20) | RAW(20) | SO/SI 포함 20바이트 |
| MEIGI_KANA | PIC X(20) | RAW(20) | 정렬 키 |
| SHUBETSU | PIC X(01) | CHAR(1) | 1=普通 2=当座 |
| ZANDAKA | PIC S9(11) COMP-3 | NUMBER(11) | |
| KAISETSU_BI | PIC 9(08) | CHAR(8) | YYYYMMDD |
| JOUTAI | PIC X(01) | CHAR(1) | 0=正常 9=凍結 |

### 3.2 取引 저널 — `TORIHIKI`
| 물리명 | COBOL | Oracle | 비고 |
|---|---|---|---|
| TORIHIKI_ID | PIC 9(12) | NUMBER(12) | PK |
| KOUZA_NO | PIC 9(10) | NUMBER(10) | FK |
| TORIHIKI_DT | PIC X(14) | CHAR(14) | 비교 시 마스킹 대상 |
| TORIHIKI_KBN | PIC X(01) | CHAR(1) | 1=入金 2=出金 3=振込 |
| KINGAKU | PIC S9(11) COMP-3 | NUMBER(11) | |
| AITE_KOUZA | PIC 9(10) | NUMBER(10) | 振込만 |
| TESURYO | PIC S9(05) COMP-3 | NUMBER(5) | 振込만 |
| TEKIYOU | PIC X(40) | RAW(40) | 漢字·카나 혼재, SO/SI, gaiji/波ダッシュ |

> DB 테이블은 컬럼을 펼쳐 보관(相手口座·手数料는 振込일 때만 채움). **REDEFINES는 파일/레코드 레이아웃 개념(§4)**이며 DB 스키마에는 넣지 않는다.

### 3.3 계정 대역 체계 (상세설계 §2)
| 대역 | 용도 | 리셋 |
|---|---|---|
| `1000000001`~`1000000099` | 시연용(결정타 집중) | 제외(보존) |
| `1000000100`~`1000000199` | 테스트용(정상) | 제외(보존) |
| `9000000001`~ | 동적(시연 중 생성) | 대상(삭제) |

- 리셋 스크립트: `DELETE ... WHERE KOUZA_NO >= 9000000000` (KOUZA·TORIHIKI 모두) + 시연용 재적재. 고정 계정은 보존.

## 4. 레코드 레이아웃 (고정길이) — 설계서 §4 그대로

> ASIS = EBCDIC(CP930). RAW 텍스트의 DBCS 구간은 SO(0x0E)/SI(0x0F)로 감쌈. COMP-3 바이트 = floor(자릿수/2)+1.

### 4.1 当日取引 입력 `TORIHIKI.DAT` (레코드 **97 byte**)
```cobol
01 TORIHIKI-REC.
   05 TR-ID           PIC 9(12).           *> 1-12   (12)
   05 TR-KOUZA-NO     PIC 9(10).           *> 13-22  (10)
   05 TR-NICHIJI      PIC X(14).           *> 23-36  (14) YYYYMMDDHHMMSS
   05 TR-KBN          PIC X(01).           *> 37     (1)  1=入金 2=出金 3=振込
   05 TR-KINGAKU      PIC S9(11) COMP-3.   *> 38-43  (6)
   05 TR-EXT          PIC X(14).           *> 44-57  (14) 種別별 재정의 영역
   05 TR-EXT-FURIKOMI REDEFINES TR-EXT.    *> ── REDEFINES(결정타) ──
      10 TR-AITE-KOUZA PIC 9(10).          *> 44-53  (10)
      10 TR-TESURYO    PIC S9(05) COMP-3.  *> 54-56  (3)
      10 FILLER        PIC X(01).          *> 57     (1)
   05 TR-TEKIYOU      PIC X(40).           *> 58-97  (40) 漢字·카나 혼재
```
- **REDEFINES(결정타)**: `TR-EXT`는 入金/出金 시 미사용(공백), 振込 시 `相手口座+手数料`로 같은 영역 재해석. COBOL의 메모리 오버레이를 **種別 분기 파싱**으로 정확히 다룬다.

### 4.2 明細レポート 출력 `MEISAI.RPT`
- 정렬: **名義カナ 오름차순(EBCDIC 순)**, 계좌별 control break.
- **레코드 길이는 58 byte로 통일(확정).** D는 그대로 58byte, T는 실내용 29byte + 공백 29byte 패딩 = 58byte.

**D 레코드 (명세, 58 byte)**
| # | 필드 | 오프셋 | byte | 타입 |
|---|---|---|---|---|
| 1 | 'D' | 1 | 1 | X(1) |
| 2 | 口座番号 | 2 | 10 | 9(10) |
| 3 | 名義漢字 | 12 | 20 | X(20) SO/SI mixed |
| 4 | 取引日時 | 32 | 14 | X(14) |
| 5 | 取引種別 | 46 | 1 | X(1) |
| 6 | 金額 | 47 | 6 | S9(11) COMP-3 |
| 7 | 取引後残高 | 53 | 6 | S9(11) COMP-3 |

**T 레코드 (계좌 합계, 실내용 29 byte → 58 byte로 공백 패딩)**
| # | 필드 | 오프셋 | byte | 타입 |
|---|---|---|---|---|
| 1 | 'T' | 1 | 1 | X(1) |
| 2 | 口座番号 | 2 | 10 | 9(10) |
| 3 | 利息 | 12 | 6 | S9(11) COMP-3 (결정타1) |
| 4 | 手数料合計 | 18 | 6 | S9(11) COMP-3 |
| 5 | 確定残高 | 24 | 6 | S9(11) COMP-3 |
| 6 | FILLER(공백 패딩) | 30 | 29 | X(29) |

## 5. 업무 규칙 (설계서 §5.3)

- 普通預金(種別=1) 年利 **0.10%**. 일 이자 = `残高 × 0.0010 ÷ 365`, **切り捨て**(1엔 미만 버림). ASIS·TOBE 동일 방식 필수.
- **当座預金(種別=2)은 무이자(利息=0) — 확정.** 이자 계산 시 種別로 분기하여 種別=1에만 계산한다.
- 振込手数料 = **정액 110엔** 引き落とし.
- 出金/振込 시 **残高不足이면 거래 거부** + 에러 레코드 출력.
- **振込은 원자적**: 出金측 차감(+수수료)과 入金측 가산을 하나의 트랜잭션으로. 실패 시 `EXEC SQL ROLLBACK`, 성공 시 `COMMIT`.
- 凍結(状態=9) 계좌 거래 처리 규칙은 프론트/설계 확인해 일관 적용(§8).

## 6. 온라인 5종 (CGI) 구현 지침

- 각 기능을 CGI 프로그램으로 구현(공통 처리 카피북/서브루틴 분리 권장).
- 요청 파싱(QUERY_STRING/stdin POST 바디)과 응답(HTTP 헤더 + 바디) 형식은 **기존 프론트의 계약에 정확히 일치**시킨다.
- **응답 인코딩은 UTF-8(확정).** HTTP 헤더에 `Content-Type: application/json; charset=UTF-8` 명시. 名義·摘要 등 CP930 RAW 값은 응답 직전에 `CP930 → CP932 → UTF-8`로 변환하여 실어 보낸다.
- 응답 바디 구조(필드명·에러 형태)는 프론트에서 추출한 계약을 따른다. GnuCOBOL JSON GENERATE/PARSE 또는 수동 직렬화 중 프론트 계약에 맞는 방식을 선택.
- 残高照会/明細照会는 조회, 入金/出金/振込은 갱신 후 TORIHIKI 저널 기록.

## 7. 야간배치 구현 지침

1. `TORIHIKI.DAT`(97byte 고정) 입력 읽기, 種別 분기(REDEFINES) 파싱.
2. 계좌별 처리 위해 **口座番号로 정렬 + control break**로 반영.
3. 반영 후 **利息·手数料** 계산(§5 규칙: 種別=1만 이자, 切り捨て).
4. 확정 잔액으로 `KOUZA` 갱신(更新後口座マスタ).
5. `MEISAI.RPT` 출력 시 **名義カナ 오름차순(EBCDIC 순)**으로 정렬 — 결정타2 노출. **모든 레코드 58byte 고정**(T는 공백 패딩).
6. 골든 OUTPUT은 실제 배치를 돌려 **EBCDIC 바이트 그대로** 생성(現新비교 툴 입력용). 배치 출력은 UTF-8 변환하지 않는다.

## 8. ⛔ 임의로 정하지 말고 확인 후 진행할 미확정 항목 (STOP & ASK)

아래는 설계서 TODO(§8) 및 도출된 쟁점 중 **아직 확정되지 않은** 것들이다. 가정하지 말고, 네 권고안 + 질문을 먼저 제시하라.
(※ 온라인 응답 인코딩=UTF-8, 明細レ포트 58byte 통일, 当座 무이자는 **이미 확정**되어 §0.1·본문에 반영됨.)

1. **API 계약** — 프론트에서 추출한 엔드포인트/요청·응답 스키마 요약표를 제출해 확인받은 뒤 구현.
2. **각 필드 자릿수·COMP-3 바이트 최종 확인** — 특히 S9(11)=6byte, S9(05)=3byte, 부호 니블·최대값·음수 표현.
3. **이행 원천 형태** — 시연 내러티브의 "CSV로 받는다"와 EBCDIC 원본의 정합(배치 입력은 EBCDIC 고정길이 원본 기준).
4. **凍結(状態=9) 계좌 거래 규칙** — 거래 거부 방식/에러 표현.
5. **gaiji 대상 문자·IBM UDC 매핑 테이블** — 髙/﨑 등. 팀 인코더 커버 범위 확인 후 반영.
6. **팀 인코더 연동 방식**(별도 툴 호출 vs DataBridge 라이브러리) — 현재는 인터페이스(`CP930 bytes → CP932`)만 고정. 온라인은 여기에 `CP932 → UTF-8` 한 단계 더 붙임.

## 9. 산출물 / 디렉터리 구조

```
asis/
  cobol/           # .cbl 온라인 5종 + 배치, 카피북 *.cpy
  sql/             # Oracle DDL, 시드(시연/테스트 고정 계정), 리셋 스크립트
  cgi/             # nginx→CGI 라우팅 설정, 실행 바이너리 배치
  build/           # gixpp 프리컴파일 + cobc 컴파일 스크립트(Makefile 등)
  docker/          # asis-backend Dockerfile(GnuCOBOL+GixSQL+Instant Client), compose 조각
  data/            # TORIHIKI.DAT 샘플(EBCDIC 고정길이), 배치 OUTPUT 검증용
  README.md        # 빌드·구동·리셋·시연 순서
```

- Docker compose 서비스: `asis-backend`(CGI), `oracle`(Free, 1521). NLS_LANG 명시.
- init 스크립트로 DDL + 시드 자동 적재. VM 재부팅 시 자동 복구(restart 정책).

## 10. 작업 순서 & 검증

1. §1 자료 정독 → **API 계약 요약표 + §8 확인 질문 제출**(승인 대기).
2. 승인 후: DDL/카피북 → 시드/리셋 스크립트 → 온라인 5종 → 배치 → 빌드·Docker.
3. 각 단계 검증:
   - 레코드가 정확히 97byte / 58byte(D·T 모두)인지 바이트 단위 확인.
   - COMP-3 저장/복원 라운드트립(최대값 9999999999, 음수 -50000 포함) 정상.
   - RAW 컬럼 CP930 바이트가 SO/SI 포함 무손실 왕복(EXEC SQL 호스트 변수 무변환) 확인 — **최우선 검증 스파이크**.
   - 온라인 응답이 UTF-8로 정확히 나가는지(CP930→CP932→UTF-8 왕복), 프론트가 무변경으로 렌더링되는지 확인.
   - 주인공 계좌(鈴木一郎左衛門)의 名義漢字가 X(20) 경계에서 자르는 위치 확인(결정타3).
   - 배치 정렬이 名義カナ EBCDIC 순인지(결정타2), 利息 切り捨て 정수 일치(결정타1), 当座 계좌 이자=0 확인.
   - 振込 원자성(중간 실패 시 롤백) 확인.

**중요:** 위 §8 미확정 항목은 확인 전 임의 결정 금지. 불명확하면 진행을 멈추고 질문할 것.
